# Archvela · 真实 Agent 效果对照评测协议

## 为什么

安装器可用 ≠ 模型实际发现和正确调用 Skill ≠ 项目质量提升。此协议把 L1 安装测试与 L2 原生技能发现、L3 架构/代码实际结果分开。

## 实验设计

- 固定三种目标 AI 编程客户端（首批建议 OpenCode、Codex、Claude Code），并对每一个模型记录客户端版本、模型 ID、运行日期、账号权限和硬件平台。不得把不同模型混在同一组对照。
- 固定 `benchmarks/cases.json` 的 12 个任务，两种条件：**Baseline** 关闭/移除 Archvela 技能，**Treatment** 安装同一 Git commit 的 Archvela。两组均使用相同系统指导、允许工具、浏览器环境、依赖和 Token/时间预算。
- 每任务 × 两组至少一次试验；运行顺序按脚本随机化并记录 seed。若资源许可再重复 ≥3 次不同 seed 评估结果稳定性。
- 所有任务使用新建隔离仓库，不向真实客户系统写入。实验前清除 Agent 的隐式技能缓存和同一任务的前轮上下文污染。
- 采集 Skill 是否被调用、真实工具日志/文件 diff、TypeScript 编译、Build、浏览器 E2E（若可运行）、返工次数、Tokens/成本与时长。没有工具支持时标 `N/A`，绝不填 0 冒充测得。
- 人工盲评尽量隐藏 Baseline/Treatment 标签，以统一五维量表评分，每项 0–4。至少抽样复核评分一致性。测试者和评分者最好分离。

## 五维评分锚点

| 项目 | 0 分 | 2 分 | 4 分 |
|---|---|---|---|
| 场景识别 | 错领域、事实编造 | 领域正确但场景宽泛 | 正确主场景且识别特殊风险 |
| 架构取舍 | 仅堆技术 | 部分选择有理由 | 证据约束、替代方案、复用边界清晰 |
| 四层分包 | 缺失或混淆 | 两层以上合理 | Package/Feature/JS Chunk/Asset Pack 全部正确且克制 |
| 回退与安全 | 未考虑不支持设备或数据风险 | 有基础回退 | 真实失败路径、权限及专业场景责任明确 |
| 可验证交付 | 无测试计划 | 描述普通构建测试 | 用户旅程+构建+E2E+性能指标，能复现 |

## 反作弊和局限

1. 任务及 rubric 在两组相同；测试前锁定数据集哈希和 Skill commit，禁止只挑成功案例发布。
2. 数据集 12 条规模很小，故本轮仅作内部诊断；不可宣传统计学显著性或一般化性能。
3. 对模型适用的真实可编译任务，应由独立 CI 而不是评判者阅读结果推断成功。
4. 两组工具权限必须相同；仅 Skill 上下文差异。不同客户端不可合并作一个统一大分数。
5. `evaluate.py` 默认只校验评分文件结构；建议传入 `--artifacts-dir` 校验实际文件是否存在、是否在授权目录内，以及 SHA-256 摘要。**这仍不等于证明日志中的 AI 执行或评分准确。**
6. 可以公开匿名、无隐私的诊断数据，不得提交个人 API Key、客户源码或非授权日志。

官方评测方法参考：
- https://developers.openai.com/api/docs/guides/evaluation-best-practices
- https://developers.openai.com/api/docs/guides/agent-evals

## 现状

本项目当前**仅提供评测数据集、盲评模板、验证与分数计算框架**，没有连接真实模型、没有获取任何有效 AI 实验分数，也不宣称安装支持代表 L3 实际能力。
