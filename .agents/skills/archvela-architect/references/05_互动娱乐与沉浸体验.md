# 05｜互动娱乐与沉浸体验：3D 网页游戏、2D 游戏、数字展厅与虚拟发布会

> 领域定位：用户通过**操作、探索、反馈和沉浸**获得体验。游戏以帧时间、战斗反馈、输入一致性和关卡资产流水线为核心；展厅以真实内容、可用性和叙事为核心。遵循 [00 通用规范](./00_通用_单人产品工厂与前端架构规范.md)。

## 1. 场景选型矩阵

| 场景 | 推荐引擎/前端 | 擅长能力 | 不推荐做法 |
|---|---|---|---|
| **3D 英雄塔防 / RPG** | **Babylon.js + TypeScript + React UI** | 骨骼动画、技能粒子、3D 战场、状态与战斗逻辑 | 把角色位移写成 React 每帧 setState |
| **3D 可视化编辑型游戏** | **PlayCanvas + React UI** | 可视化场景编辑、PBR、WebGL2/WebGPU 回退 | 为纯代码项目先造复杂编辑器 |
| **2D 塔防 / 横版 / 卡牌** | **Phaser** | 2D 游戏循环、碰撞、场景、音频、输入 | 为简单 2D 引入 3D 引擎 |
| **海量 2D 精灵 / 特效** | **PixiJS** | GPU 批绘、精灵、粒子、滤镜 | 自己从零造完整游戏框架而无必要 |
| **交互式数字展厅** | R3F 或 PlayCanvas | 模型、热点、动画、空间导航、屏幕视频 | 一开始实现多人在线等重功能 |
| **沉浸式品牌发布会** | Next.js + R3F + GSAP + Video | 品牌叙事、交互展示、镜头时间线 | 完全依赖高性能 GPU，忽略低端设备 |
| **数字博物馆 / 文旅** | Three.js / PlayCanvas + Gaussian Splatting（按需） | 空间探索、文物/环境展示、路径导览 | 未许可的博物馆/游戏资产直接商用 |
| **XR 导览** | WebXR + 适配的 Three/Babylon/PlayCanvas | 沉浸头显、控制器/空间交互 | 默认所有浏览器具备完整 XR 功能 |
| **高画质 Unity Web 项目** | Unity 自带 Web 构建 + 独立 React 门户 | 成熟游戏编辑、动画、特效、可跨平台 | 期待 Unity 引擎内部源码由 Next.js 打包 |
| **Unreal 远程高保真体验** | Unreal + Pixel Streaming + 前端承载页 | GPU 远端渲染、浏览器接收视频流 | 混淆“云端视频串流”和“原生浏览器渲染” |

## 2. Babylon.js、PlayCanvas、Three.js 怎么选？

| 维度 | Babylon.js | PlayCanvas | Three.js + R3F |
|---|---|---|---|
| 最合适 | 完整 3D 游戏 | Web 原生 3D/可视化场景制作 | 高度自定义 React 三维交互 |
| 游戏循环 | 引擎内管理 | 引擎内管理 | 自定义职责更多 |
| 角色与特效 | 骨骼/动画/物理/粒子完整 | 动画图/后处理/物理/粒子 | 生态组合实现 |
| 场景编辑 | 提供工具但主要自主组织 | **可视化 Editor 优势突出** | 自己选择工具链 |
| WebGPU | 具备相关支持，按版本验收 | 支持且可回退 WebGL2 | 当前生产优先 R3F v9/稳定 WebGL |
| React UI | 分离 HUD/React 组件 | 支持 React 集成 | React 最自然 |
| 单人优先级 | **代码驱动游戏首选** | **编辑器驱动可选** | 非游戏中心的创意 3D 首选 |

**决定标准**：如果你要直接用 OpenCode 写 TypeScript 战斗框架，以 Babylon.js 原型开始；如果主要在可视化 Editor 中摆场景和调整镜头，以 PlayCanvas 原型开始。完成同等战斗小关卡后测启动、构建、帧率和开发负担再确认。

## 3. 类似奇幻英雄塔防玩法的“独立原创”产品设计

可参考英雄布阵、战斗节奏和养成深度，但**不得复制具体游戏的角色、美术、技能素材、音乐、UI 文案或商标**。为降低个人开发负担，第一版采用原创低数量角色和可复用模块。

### 3.1 核心游戏闭环

选择关卡 → 选择英雄与布阵位置 → 敌人沿导航路线来袭 → 自动攻击/手动技能 → 胜负结算 → 角色配置/重试。

第一版范围：**1 张地图、3 名原创英雄、2 类怪物、5 波进攻、2 种技能、胜负与重试**。完成可玩关卡优先于英雄抽卡/付费/海量养成。

### 3.2 必要的前端/引擎系统

| 系统 | 职责 | 实现边界 |
|---|---|---|
| Game Loop | 固定步长模拟、渲染帧插值 | 状态与渲染时钟分离 |
| Entity System | 单位生命周期、属性、阵营、出生/销毁 | ECS 可选，早期数据驱动对象足够 |
| Placement | 布阵点、单位占位与合法性反馈 | 逻辑坐标，不依赖 Mesh 名称 |
| Targeting | 攻击范围、敌人筛选、目标变更 | 纯函数可测试 |
| Pathfinding | 路线图/导航网格、转角、避障（按需） | 不一定需要物理引擎；先用固定路线 |
| Combat | 冷却、伤害、治疗、Buff、控制 | 时间与取值可重复测试 |
| Animation | 站立、跑、攻击、受击、死亡 | GLB Skeleton/Animation Groups |
| VFX | 火焰/风暴/范围指示、命中反馈 | GPU Particle/Shaders，移动质量分级 |
| HUD | 血量、波次、技能按钮、暂停菜单 | React 与引擎事件桥通信 |
| Asset Manager | GLB、贴图、音频、预加载、缓存 | 按地图与波次切包 |
| Input | 鼠标、触控、手柄/键盘按需 | 浏览器事件归一层 |
| Save UI | 本地存档状态、导入导出、失败提示 | 前端只实现可验证的保存契约 |

### 3.3 固定步长逻辑和渲染分离

```ts
const FIXED_STEP = 1 / 30;
let accumulator = 0;

function tick(deltaSeconds: number) {
  accumulator += Math.min(deltaSeconds, 0.1);
  while (accumulator >= FIXED_STEP) {
    simulateCombat(FIXED_STEP); // 纯逻辑/有界副作用
    accumulator -= FIXED_STEP;
  }
  renderScene(accumulator / FIXED_STEP); // 使用快照做插值
}
```

这是**概念伪代码**；真实引擎应使用其官方渲染循环，处理暂停、切后台、资源加载和更新顺序，不能直接把上面的函数当成引擎可运行代码。

**React UI 交互协议**：HUD 发 `useSkill(heroId,target)`；游戏逻辑返回 `skillAccepted` / `skillRejected`、CD 和状态快照；3D 场景只读取快照做画面，不让 UI 直接改变渲染 Mesh 充当业务状态。

## 4. 游戏与数字展厅的文件结构

```text
src/
  game/
    bootstrap.ts                # 引擎生命周期与入口
    state/                      # 游戏域状态/事件
    combat/                     # 纯战斗运算
    navigation/                 # 格子/路径
    systems/                    # 动画、战斗、音频等
    engine-adapters/
      babylon/                   # 引擎绑定与资源管理
    scenes/
      title/
      stage-001/
    assets/
      manifest.ts               # 关卡资产和 checksum
      loaders.ts
  ui/
    components/
    hud/
    menus/
    accessibility/
  contracts/
  design/
public/
  game/
    common/
    stages/stage-001/
    audio/
    posters/
```

PlayCanvas 可以将 `engine-adapters/babylon` 换成 `engine-adapters/playcanvas`；引擎资源不必共享，两者不是一套可无成本热切换的 API。

**商用数字展厅**：游戏模块换为 `tour`, `exhibits`, `narration`, `hotspots`；用叙事与空间锚点组织，不要用战斗系统抽象展厅。

## 5. 资产分包与资源流水线

| 资源组 | 预加载规则 | 注意 |
|---|---|---|
| Shell + 菜单 | 立即 | 保证按钮、设置、下载进度可用 |
| 公共材质/字体/图标 | 页面进入 | 品牌技能图标不同于 Lucide 线性图标 |
| 关卡地图 GLB | 选择关卡后 | LOD/拆分、尽早显示缩略预览 |
| 英雄模型与骨骼 | 阵容确认前按需下载 | 复用材质、动画状态图 |
| VFX / Shader | 即将用到的技能前 | 版本兼容和移动端降质 |
| 音频 | 用户授权后解锁，分关卡加载 | 兼容浏览器自动播放限制 |
| 下一波敌人 | 当前波运行时低优先预加载 | 限制并发、处理失败 |
| 额外地图/剧情 | 不进入首包 | 边界清晰，重复进入可缓存 |

**美术管线**：原生资产 → Blender/授权编辑器 → glTF/GLB → 纹理压缩 KTX2（按需）→ Meshopt/Draco → 模型检查器 → 在目标手机真机验收。材质、动画命名、单位、坐标轴与资源哈希都要记录。

## 6. 沉浸式非游戏体验模板

### 6.1 虚拟展厅

入口 Poster → 点击进入 3D → 空间漫游 → 展品热点 → 文字/视频讲解 → 联系/收藏。优先实现能被引导理解的导航，而不是无尽自由漫游。

### 6.2 数字博物馆

按展品组织：真实版权来源、模型高/低精度、3D 交互、文字说明、讲解音频、无障碍资料。Gaussian Splatting 可用于沉浸式现实场景，但它不是默认适合精确构件量测的格式。

### 6.3 虚拟发布会

Next.js 提供内容和导航；浏览器视频为主，Three.js/R3F 仅渲染可互动展品；GSAP 用于分镜时间轴；弱网和无 WebGL 必须保持产品信息可用。

## 7. 性能质量与降级计划

| 主题 | 目标/方法 | 降级 |
|---|---|---|
| 流畅度 | 桌面 60 FPS、移动 30 FPS 起始目标，实测帧时间 P95 | 减少粒子、后处理、动态阴影 |
| CPU/GPU | 不对每个怪物触发 React 高频更新 | 降低模型细节、频率、实例化 |
| 网络 | 首关资产明确预算，增量下载 | 下载暂停/重试、静态资源提示 |
| 崩溃 | Context Lost、内存峰值、切后台恢复 | 释放资源、回主菜单/设置画质 |
| 输入 | 鼠标/触控行为一致，技能冷却明确 | 可切换点击/快捷键模式 |
| 动态效果 | 屏闪、相机晃动、眩晕可调 | reduced-motion、低闪烁模式 |
| 版权 | 角色模型、音乐、特效/字体授权可追溯 | 不可验证素材不上线 |
| 安全状态 | 对战/胜负/存档状态来源清晰 | 模拟局仅标识本地演示 |

## 8. 可测试的战斗逻辑约束

- 固定 RNG 种子时，目标选择、伤害计算和战斗日志可复现（若使用随机数）。
- 冷却在暂停与后台切换时规则明确，不随 FPS 改变伤害。
- 角色死亡、技能触发、敌人到达终点、波次结算在逻辑上无竞争重复。
- 每个动画事件要有超时/回退，不能依赖“动画播完”才提交不可逆状态。
- 真实设备上验收 1x/2x DPI、触控、窗口切换、失去 WebGL 上下文。

## 9. 单人开发的首个 MVP

**第一闭环**：开场菜单 → 开始关卡 → 摆放一个英雄 → 敌人行进 → 自动攻击 → 手动技能 → 胜/负 → 重试。

分阶段只扩展一个系统：先战斗正确，再动画与音效，再图形质量，最后才是扩充角色。切勿在游戏机制未验证时先产出几十张角色原画与数百套技能特效。

